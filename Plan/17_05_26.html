📋 Mục 1: Khái Quát Kế Hoạch

Mục tiêu: Phân tích toàn diện dự án Flutter "Lá chắn cuộc gọi" để tìm ra và khắc phục các điểm nghẽn gây bug, lag/giật, nóng máy, tốn pin.

Phạm vi: 30+ file Dart (lib/), 12+ file Kotlin (android/), cấu trúc analysis L1-L2-L3, MonitoringPage, EventChannel streams, TFLite model, Gemini API, SQLite database.

Kết quả mong đợi:

  • Giảm ≥60% CPU usage trong quá trình monitoring
  • Loại bỏ memory leak từ EventChannel streams
  • Giảm latency phân tích real-time xuống dưới 200ms
  • Tăng tuổi thọ pin khi chạy background service
  • Ứng dụng hoạt động mượt 60fps không giật

🔬 Mục 2: Phân Tích Chi Tiết Các Điểm Nghẽn

CRITICAL #1 — EventChannel Stream tạo mới mỗi lần truy cập (Memory Leak)

File: native_call_shield_bridge.dart dòng 347-375

Vấn đề: Các getter transcriptStream, rmsStream, monitoringStateStream, callEventStream gọi receiveBroadcastStream() mỗi lần truy cập → tạo stream mới, stream cũ không cancel → memory leak + trùng lặp events.

Cách sửa: Cache stream bằng late final hoặc private field, chỉ tạo một lần.

  • ✅ Ưu: Loại bỏ hoàn toàn memory leak, giảm CPU từ duplicate processing
  • ❌ Nhược: Cần test kỹ lifecycle khi app bị kill/restart

CRITICAL #2 — MonitoringPage tạo L1+L2+L3 Analyzer mới mỗi lần navigate (Nóng máy)

File: monitoring_page.dart dòng 101-108

Vấn đề: Mỗi lần vào MonitoringPage → L1Analyzer(), L2Analyzer(), L3Analyzer() được tạo mới → load lại toàn bộ JSON assets, build Trie, load TFLite model → tốn 500ms-2s CPU spike, nóng máy.

Cách sửa: Chuyển sang Riverpod Provider (singleton), chỉ khởi tạo một lần khi app start.

  • ✅ Ưu: Tiết kiệm 500ms-2s mỗi lần navigate, giảm RAM ~20MB
  • ❌ Nhược: Cần quản lý lifecycle session reset cẩn thận

CRITICAL #3 — RMS Stream gây rebuild liên tục (Giật UI, Tốn pin)

File: monitoring_page.dart dòng 221-234

Vấn đề: RMS stream phát events ~20 lần/giây (throttle 50ms). Mỗi event: removeAt(0) trên List (O(n)), tạo List.from() mới → GC pressure. Dù có RepaintBoundary, ValueNotifier vẫn trigger build của parent widget.

Cách sửa: Dùng circular buffer thay List; tăng throttle lên 100ms; dùng addPostFrameCallback để batch updates theo frame.

  • ✅ Ưu: Giảm 50% rebuild, giảm GC pressure, UI mượt hơn
  • ❌ Nhược: Waveform animation có thể kém smooth hơn nhẹ

HIGH #4 — L2 chạy 3 engine song song không giới hạn (CPU spike)

File: l2_analysis.dart dòng 126-131

Vấn đề: _runIntentFlow() (TFLite) + performFullAnalysis() (GDetection) chạy đồng thời. TFLite dùng tối đa 4 threads. GDetection tokenize + trie search + pattern match + scenario match cùng lúc. Kết hợp với L1 cũng có thể chạy đồng thời → CPU 100% → nóng máy, giật.

Cách sửa: Thêm semaphore/mutex giới hạn concurrent analysis; chạy TFLite trên isolate riêng.

  • ✅ Ưu: Kiểm soát CPU usage, tránh thermal throttling
  • ❌ Nhược: Tăng latency nhẹ do chờ đợi

HIGH #5 — Analysis Debounce quá ngắn 600ms (Phân tích dư thừa)

File: monitoring_page.dart dòng 712

Vấn đề: Debounce 600ms cho real-time analysis. Với transcript stream phát liên tục, analysis chạy ~1.5-2 lần/giây. Mỗi lần chạy: tokenize + trie + TFLite + WFSA → CPU spike lặp lại liên tục. MinDelta trong coordinator chỉ 20-50 chars, không đủ ngăn chặn.

Cách sửa: Tăng debounce lên 1200-1500ms; thêm check "đang phân tích thì skip"; adaptive debounce dựa trên risk level.

  • ✅ Ưu: Giảm 50-60% số lần phân tích, tiết kiệm pin đáng kể
  • ❌ Nhược: Cảnh báo có thể chậm hơn 0.5-1s

HIGH #6 — L1 Fuzzy Matching O(n*m) trên mỗi unmatched token (Lag)

File: l1_analysis.dart dòng 279-303

Vấn đề: Với mỗi token không match, FuzzyMatcher.findClosest() duyệt toàn bộ _singleTokenKeywords (hàng trăm keywords), tính Levenshtein distance O(m*n) cho mỗi cặp → O(tokens * keywords * avgLen²). Khi transcript dài → lag rõ rệt.

Cách sửa: Pre-filter theo length ±1; cache kết quả fuzzy; giới hạn max unmatched tokens xử lý; dùng BK-tree.

  • ✅ Ưu: Giảm 80% thời gian fuzzy matching
  • ❌ Nhược: Có thể miss một số fuzzy match edge case

HIGH #7 — GDetection Engine re-initialize mỗi lần L2 được tạo mới

File: g_detection_engine.dart dòng 62-83

Vấn đề: Liên quan đến Bug #2 — mỗi lần MonitoringPage mới tạo L2Analyzer mới → GDetectionEngine mới → load 8 file JSON, build Trie, parse patterns → 200-500ms blocking + RAM spike.

Cách sửa: Singleton pattern cho GDetectionEngine hoặc Riverpod Provider.

  • ✅ Ưu: Loại bỏ hoàn toàn overhead re-initialization
  • ❌ Nhược: Cần lazy init mechanism

HIGH #8 — DeveloperMode Timer chạy mỗi giây khi active (Tốn pin)

File: developer_mode_manager.dart dòng 147-161

Vấn đề: Timer.periodic(1 second) cập nhật state mỗi giây → Riverpod rebuild mỗi giây → UI rebuild không cần thiết. Kéo dài 10 phút = 600 lần rebuild vô ích.

Cách sửa: Chỉ cập nhật khi UI thực sự hiển thị remaining time; dùng interval lớn hơn (10-30s); hoặc chỉ check on-demand.

  • ✅ Ưu: Loại bỏ 600 rebuild vô ích
  • ❌ Nhược: Countdown hiển thị kém chính xác hơn (nhưng acceptable)

MEDIUM #9 — SettingsController._load() race condition

File: settings_controller.dart dòng 43-51

Vấn đề: build() trả về default state rồi gọi _load() async. Trong khoảng thời gian SharedPreferences chưa load xong, UI dùng default settings (gDetection mode) thay vì user setting → có thể trigger wrong analysis mode ban đầu.

Cách sửa: Dùng AsyncNotifier hoặc load settings trước khi runApp().

  • ✅ Ưu: Đảm bảo settings đúng ngay từ đầu
  • ❌ Nhược: Có thể tăng thời gian khởi động ~50ms

MEDIUM #10 — MonitoringPage có 758 dòng (God Widget)

File: monitoring_page.dart

Vấn đề: Một widget 758 dòng chứa: UI, business logic, stream management, analysis orchestration, session management, navigation → khó maintain, dễ bug, khó test.

Cách sửa: Tách thành MonitoringController (Riverpod Notifier) + MonitoringPage (UI only).

  • ✅ Ưu: Dễ test, dễ maintain, giảm rebuild scope
  • ❌ Nhược: Cần refactor lớn, nhiều file mới

MEDIUM #11 — L3 Gemini API không có timeout/retry strategy

File: l3_analysis.dart, gemini_client.dart

Vấn đề: API call có thể hang vô thời hạn khi mạng chậm. consecutiveErrors chỉ track nhưng không có circuit breaker → tiếp tục gọi API thất bại → tốn pin cho network requests vô ích.

Cách sửa: Thêm timeout 10s; circuit breaker (dừng sau 3 lỗi liên tiếp, chờ 60s); exponential backoff.

  • ✅ Ưu: Tiết kiệm pin, tránh hang, failover nhanh hơn
  • ❌ Nhược: Cần tuning threshold phù hợp

MEDIUM #12 — HomePage permission check popup mỗi lần quay lại

File: home_page.dart dòng 23-38

Vấn đề: _checkAndRequestPermissions() gọi trong initState → mỗi lần navigate về Home → hiện dialog xin quyền lại nếu chưa đủ → UX khó chịu + có thể chồng dialog.

Cách sửa: Chỉ hiện dialog lần đầu dùng SharedPreferences flag; hoặc chỉ hiện khi user tap "Bắt đầu giám sát".

  • ✅ Ưu: UX tốt hơn, không spam dialog
  • ❌ Nhược: User có thể quên cấp quyền
